# Loopstack 0.3 Orchestrated Loops Design

**Status:** approved direction, written specification pending owner review  
**Release:** 0.3.0  
**Compatibility floor:** every valid Loopstack 0.2 loop definition and v1/v2 handoff remains readable

## Purpose

Loopstack 0.3 must design and build reliable AI loops inside real business processes without pretending that every process step is itself an AI loop. It separates the business workflow, the control loop, and the runtime agent loop while preserving one coherent owner journey from discovery through operation.

The reference case is a photovoltaic administration process triggered when a technical visit is validated. The deterministic backbone collects documents, prepares and tracks mairie and Enedis submissions, waits for external responses, resumes after human decisions, and closes the case. AI capabilities read and classify documents, detect ambiguity, draft material, and propose improvements. A control loop measures cycle time, rejection rate, completeness, and intervention outcomes.

## Approaches considered

### A. Additive orchestrated-loop contracts — selected

Extend the existing schemas with optional typed process, trigger, guardrail, human-gate, work-item, learning-proposal, and runtime-deployment contracts. Existing 0.2 inputs normalize into safe 0.3 defaults. Design artifacts show both the business state machine and the six-stage control loop when the process is asynchronous.

This approach preserves compatibility, gives production loops stronger guarantees, and keeps the seven public skills unchanged.

### B. Replace the 0.2 loop schema

A clean breaking schema would be simpler internally, but it would invalidate persisted loops, examples, runtime packages, and integrations. The migration cost is not justified.

### C. Documentation-only guidance

Adding prose about workflows and gates would be fast, but the runtime could still accept ambiguous triggers, unstructured approvals, and loops with no resumable work-item model. This would not make generated loops safer or executable.

## Conceptual model

Loopstack uses three distinct layers:

1. **Business process** — states, transitions, waits, deadlines, external submissions, owners, and human decisions for one durable work item.
2. **Control loop** — `Target → Observe state → Evaluate/Plan → Act → Observe result → Evaluate outcome → Learn → Decide`, which measures and improves operation of the business process.
3. **Agent runtime loop** — the runtime's internal reason/tool/observe cycle. Loopstack constrains it but does not model each reasoning turn as a business state.

The canonical Loopstack 0.3 cycle is:

```text
Target
→ Observe state
→ Evaluate / Plan
→ Act
→ Observe result
→ Evaluate outcome
→ Learn
→ Decide
   ├─ continue → Observe state with the new evidence
   ├─ wait-human
   ├─ wait-external
   ├─ stop-success
   ├─ stop-failure
   └─ escalate
```

The two observation/evaluation moments must remain visible because they answer different questions. Before the action, the loop observes current reality and plans the next bounded intervention. After the action, it observes what actually happened—including unknown or partial side effects—and evaluates quality, progress, policy, and guardrails before learning or continuing.

Compact summaries may group both observations under `Observe` and both evaluations under `Evaluate`, but generated process contracts, prompt-cycle traces, tests, and owner blueprints must preserve the pre-action and post-action distinction.

## Agent prompt-cycle controller

An AI Loop must contain an executable controller that prompts one or more agents repeatedly. A state machine, cron job, automation, or dashboard without this controller is not sufficient to qualify as an AI Loop.

For every iteration the controller:

1. loads the target and observes the current work item, latest evidence, prior action result, feedback, gates, budgets, and stop conditions from durable state;
2. evaluates the gap and builds a versioned `AgentRunRequest` containing the bounded plan rather than relying on conversational memory;
3. invokes the maker through the selected runtime with declared skills and least-privilege tools so it can act;
4. observes and persists the actual agent output, tool/action evidence, token/cost usage, and side-effect state, including `unknown` outcomes;
5. evaluates the outcome with deterministic checks and, when declared, a separate checker-agent request;
6. records learning evidence and creates a governed learning proposal only when thresholds are satisfied;
7. resolves exactly one next decision: `continue`, `wait-human`, `wait-external`, `stop-success`, `stop-failure`, or `escalate`;
8. on `continue`, creates the next request from newly persisted evidence and prompts the agent again.

The request contract is:

```yaml
agentRunRequest:
  loopId: pv-admin
  runId: run-2026-08-04-001
  iteration: 3
  role: maker
  promptTemplateVersion: 2
  inputSnapshotHash: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  target: dossier_submission_cycle_hours
  workItemId: dossier-client-123
  currentState: collecting-documents
  observations: [observation-41, observation-42]
  previousEvaluation: evaluation-12
  allowedActions: [request-document, prepare-mairie-preview]
  forbiddenActions: [submit-mairie]
  skills: [pv-admin-playbook, document-qa]
  limits:
    maxIterations: 8
    maxCost: 4.00
    deadline: 2026-08-04T12:00:00Z
```

The checker request uses the same evidence snapshot with `role: checker`, a distinct prompt/template version, no consequential write tools, and an explicit rubric. Maker and checker may be the same underlying model but are separate agent invocations and audit records.

The controller depends on three ports so orchestration stays testable and runtime-neutral:

```typescript
interface AgentInvoker {
  invoke(request: AgentRunRequest): Promise<AgentRunResult>;
}

interface PromptCycleStore {
  loadCheckpoint(loopId: string, workItemId: string): Promise<PromptCycleCheckpoint | null>;
  saveCheckpoint(checkpoint: PromptCycleCheckpoint): Promise<void>;
  appendResult(result: AgentRunResult): Promise<void>;
}

interface CycleEvaluator {
  evaluate(input: EvaluationInput): Promise<CycleDecision>;
}
```

`AgentRunResult` records the request id, output artifact references, action attempts and side-effect states, observations, token usage, cost, and progress fingerprint. `CycleDecision` is the closed enum listed above and carries a reason plus the next allowed actions when it returns `continue`.

Every cycle is bounded by maximum iterations, cost, wall-clock deadline, tool permissions, and consecutive no-progress count. The controller persists a checkpoint before invoking an agent and after every result, so an interrupted process resumes from state instead of replaying a consequential action. Recursive agent self-prompting, unbounded retries, and invisible in-memory continuation are forbidden.

## Classification and architecture shape

Qualification continues to select exactly one system classification:

- AI Loop;
- AI-assisted workflow;
- deterministic automation;
- on-demand agent task;
- monitoring/reporting;
- human SOP/approval process;
- data pipeline;
- one-time project;
- multiple independent loops requiring decomposition.

When the classification is `AI Loop`, it also selects one architecture shape:

- `control-loop` — one recurring unit with no long-lived business state machine;
- `workflow-with-control-loop` — a durable state machine with embedded AI decisions and one control loop;
- `multi-loop-system` — separately owned loops with explicit interfaces and independent feedback horizons.

Deterministic or AI-assisted processes do not become fake loops. Discovery produces a recommended non-loop architecture and stops. A workflow with a genuine feedback cycle may qualify as an AI Loop using `workflow-with-control-loop`.

## Loop definition v3

The existing `target`, `current`, `triggers`, `feedback`, and `approval` fields remain valid.

### Primary target and guardrails

`target` remains the single north-star metric. It gains optional `direction` and `sourceOfTruth` fields. A loop may also declare:

```yaml
guardrails:
  - metric: administrative_rejection_rate
    operator: lte
    threshold: 0.08
    sourceOfTruth: crm
    evaluationWindowDays: 90
serviceLevels:
  - metric: dossier_submission_cycle_hours
    operator: lte
    threshold: 192
    appliesTo: 0.90
```

Guardrails can stop, pause, or escalate a run but cannot silently replace the north-star.

### Typed triggers

Each trigger supports:

```yaml
id: visit-validated
type: event
role: primary
enabled: false
source: crm
event: technical_visit.validated
idempotencyKey: client_id+visit_version
debounceSeconds: 30
replayWindowHours: 72
payloadSchemaRef: schemas/technical-visit-validated.json
configuration: {}
```

`role` is `primary`, `recovery`, `watchdog`, or `resume`. Existing 0.2 triggers normalize to `role: primary` and `enabled: false`. Activation always rejects an already-enabled unapproved trigger. A recovery cron is distinct from the primary event and must explain which missed or stalled cases it recovers.

### Typed human gates

Approval policy retains `mode`, `requiredFor`, and `approvers`, and gains `gates`:

```yaml
gates:
  - id: approve-mairie-submission
    beforeAction: submit-mairie
    risk: high
    conditions: [official-submission]
    evidenceArtifacts: [mairie-dossier-preview.pdf]
    choices: [approve, edit, reject, request-information]
    approvers: [admin-owner]
    timeoutHours: 48
    onTimeout: escalate
    onReject: collecting-documents
    resumeFrom: submit-mairie
```

A model confidence score may route a case to a gate but never independently authorize a consequential action. Gates are primarily driven by action class, financial/material threshold, missing evidence, novelty, policy, reversibility, and data conflict.

## Process definition

`process.yaml` receives a schema-backed `ProcessDefinition`:

```yaml
schemaVersion: 1
loopId: pv-admin
kind: workflow-with-control-loop
workItem:
  entityName: dossier
  idField: dossierId
initialState: collecting-documents
states:
  - { id: collecting-documents, type: active }
  - { id: awaiting-mairie, type: waiting-external, slaHours: 720 }
  - { id: awaiting-mairie-approval, type: waiting-human, slaHours: 48 }
  - { id: completed, type: terminal }
transitions:
  - from: collecting-documents
    event: dossier.complete
    to: awaiting-mairie-approval
    actor: agent
    gateId: approve-mairie-submission
```

State and event identifiers are stable lowercase kebab-case. Every transition names its actor (`agent`, `human`, `system`, or `external`), may bind one action and one human gate, and is rejected if its source state or event does not match. Terminal states have no outgoing transition. Waiting states declare an SLA or an explicit reason why no SLA applies.

The design HTML shows the business state machine and control loop as separate diagrams in one owner artifact when `kind` is not `control-loop`.

## Work-item runtime contract

Long-running processes use a canonical `WorkItem`:

```yaml
id: dossier-client-123
loopId: pv-admin
processVersion: 1
currentState: awaiting-mairie
status: waiting-external
revision: 4
externalReferences: {}
missingInputs: []
pendingGate: null
deadline: 2026-09-01T08:00:00Z
nextCheckAt: 2026-08-05T08:00:00Z
```

The transition API consumes a process definition, current work item, event id, event timestamp, and idempotency key. It returns the updated item plus an append-only transition record. Duplicate idempotency keys are deduplicated. Revision mismatches fail closed to prevent concurrent state loss.

The prompt-cycle controller owns run and iteration records but not business truth. A work-item transition occurs only after the iteration's action/evaluation contract authorizes it. Waiting for a human or external organization ends the current agent run; a resume trigger starts a new run from the persisted work item rather than keeping an agent session alive.

Storage blueprints add shared logical entities separated by `loopId`:

- `workItems`;
- `stateTransitions`;
- `externalSubmissions`;
- `deadlines`;
- `learningProposals`.

`stateTransitions` and `externalSubmissions` are append-only. Business documents and raw CRM records remain in their source of truth; the loop store holds references, hashes, statuses, and evidence only.

## Learning governance

Operational learning is mandatory; self-modification is optional.

Every loop records evidence, evaluations, and outcomes. A reusable behavior change becomes a `LearningProposal` with this lifecycle:

```text
proposed → validated → approved → promoted
        ↘ rejected
promoted → rolled-back
```

A proposal contains evidence ids from completed feedback windows, target artifact, proposed patch summary, expected metric effect, risk, test command, rollback instructions, and approver when required. It cannot target a read-only plugin skill such as `loopstack:loop-design`. Hermes proposals target a separate installed/project skill; Claude Code and Codex proposals target versioned project skills or instructions. Promotion requires passing tests and the declared approval for medium/high-risk changes.

## Runtime adapters

### Hermes

The build phase renders an inert activation plan with argument arrays, never shell-interpolated command strings. It covers native cron and webhook subscriptions, the prompt-cycle entry command, skills to load, HMAC/idempotency requirements, delivery target, and verification/removal commands. The plan remains `enabled: false` and is executed only by `loop-launch` after fresh activation approval.

Hermes internal `state.db` is never a loop store dependency. Plugin-provided skills are treated as read-only; per-loop learnings target separate mutable skills.

### Claude Code

Manual execution is native. Cron, webhook, event, and queue triggers remain external requirements and name the external scheduler/receiver contract. The runtime package includes the exact controller-to-agent invocation, request/result envelope, idempotency, work directory, allowed tools, and approval-resume behavior.

### Codex

A new `CodexRuntimeAdapter` provides render, preflight, and validation parity with Claude Code. Manual invocation is native; non-manual triggers are explicit external requirements. The package includes a `.codex-plugin/plugin.json`, skill wrapper, permissions/tool policy, work directory, and the exact controller-to-agent request/result contract.

## QA and failure behavior

The scenario executor adds:

- delayed external response;
- human approval timeout;
- invalid state transition;
- concurrent revision conflict;
- stale work item;
- partial document set;
- rejected external submission;
- learning proposal without enough feedback;
- attempt to mutate a read-only plugin skill;
- maximum iteration reached;
- no-progress threshold reached;
- checker rejection followed by a corrected next prompt;
- interrupted controller resumed from its persisted checkpoint.

Existing missing-data, low-confidence, rejected-approval, duplicate-webhook, timeout, budget, and interruption scenarios remain valid.

Unknown consequential side effects always enter reconciliation before retry. Human timeout escalates but never auto-approves. External rejection returns through an explicit state transition rather than mutating the case ad hoc.

## Public skill behavior

The seven public skills remain unchanged.

- `loop-discover` records classification plus architecture shape and uses the last real work item as evidence.
- `loop-design` produces one owner-facing HTML with separate business-process and complete pre/post-action control-loop views where applicable.
- `loop-plan` plans schema migration, per-loop skills, runtime activation operations, and rollback.
- `loop-build` creates schemas, process packages, tests, and inert activation plans.
- `loop-launch` alone may execute approved activation operations through shadow and canary stages.
- `loop-operate` monitors work-item SLAs, state distribution, guardrails, gates, learning proposals, and business feedback.

## Versioning and compatibility

All manifests become `0.3.0`. JSON schema exports remain synchronized.

Compatibility requirements:

- all current tests and fixtures continue to pass unless their expected release version changes;
- a valid 0.2 `LoopDefinition` parses and normalizes with no user migration;
- v1 and v2 handoffs keep their current behavior;
- new fields are optional at the compatibility boundary and required only when the selected architecture shape needs them;
- no runtime trigger is enabled by parsing, rendering, building, or testing;
- no migration reads or writes Hermes internal `state.db`.

## Acceptance criteria

1. A photovoltaic `workflow-with-control-loop` fixture validates, creates a work item on `technical_visit.validated`, waits at the mairie gate, resumes after approval, deduplicates the same event, and rejects an invalid transition.
2. A legacy 0.2 SEO loop still parses, renders, and passes existing tests.
3. Target guardrails and service levels are schema-validated and appear in every rendered runtime package.
4. Trigger role, disabled state, idempotency, payload reference, debounce, replay window, and recovery purpose survive normalization and rendering.
5. Human gates support approve/edit/reject/request-information, timeout escalation, and exact resume state without confidence-based auto-authorization.
6. Storage blueprints include the five new entities with append-only rules where specified and never duplicate source-of-truth documents.
7. Learning proposals cannot skip lifecycle states, cannot promote without tests/approval when required, and cannot target Loopstack plugin skills.
8. Hermes, Claude Code, and Codex adapters pass the same runtime contract suite.
9. Hermes activation plans contain exact inert cron/webhook operations and verification/removal operations but perform no external mutation during render or build.
10. The full quality gate, official skill validation, Python compilation, strict Claude manifest validation, secret/path scan, and distribution smoke tests pass.
11. An end-to-end prompt-cycle test invokes a maker, persists its result, invokes a checker, creates a second maker request after rejection, and stops after checker approval without exceeding declared limits.
12. A waiting-human or waiting-external decision terminates the current run and resumes in a new run from the durable work item when the matching trigger arrives.

## Out of scope

- a graphical hosted Loopstack control-plane product;
- automatic legal interpretation for regulated submissions;
- direct use of Hermes internal database tables;
- calibrating model confidence as an authorization mechanism;
- live activation without a fresh scope-bound approval;
- provider-specific business connectors beyond the existing native-connection contract.
